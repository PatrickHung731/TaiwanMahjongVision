# 台灣 16 張算牌演算法

## 1. 牌型表示：34 位元陣列

所有牌組（手牌、牌河、已見牌）都用 `IntArray(34)`，陣列值 = 張數：

| 索引 | 牌 |
| --- | --- |
| 0 ~ 8 | 一萬 ~ 九萬 |
| 9 ~ 17 | 一筒 ~ 九筒 |
| 18 ~ 26 | 一條 ~ 九條 |
| 27 ~ 33 | 東 南 西 北 中 發 白 |

花牌（春夏秋冬梅蘭菊竹）**不在**這個陣列裡，只用 `HandState.flowers` 記張數，
因為花牌不參與 16 張的面子組合，只影響最後計台。

## 2. 台灣規則與日本規則的差別

| | 日本麻將 | 台灣 16 張 |
| --- | --- | --- |
| 胡牌型 | 4 面子 + 1 眼 | **5 面子 + 1 眼** |
| 手牌張數 | 13（摸後 14） | **16（摸後 17）** |
| 特殊型 | 七對子、國士無雙 | 一般不採用（本引擎不實作） |

副露（吃、碰、明槓、暗槓）每一組都讓「還需要湊的面子數」少 1、手牌少 3 張，
槓雖然用掉 4 張牌，但**組合上仍只算 1 個面子**。

## 3. 向聽數：最大重疊 DP

### 3.1 為什麼不用傳統公式

日麻常見寫法是把手牌拆成「面子 + 搭子」，再套：

```
shanten = 8 - 2 * 面子數 - 搭子數      （另有區塊上限、沒眼要 +1 等修正）
```

推廣到 5 面子時公式變成 `10 - 2*面子 - 搭子`，區塊上限變 6，
但那些修正條款是經驗歸納出來的，邊界（例如 6 個區塊卻沒有對子）很容易寫錯，
而且錯了不會當掉，只會安靜地建議你切錯牌。

### 3.2 本引擎的作法

改用一個**由定義直接推導**的算法：

> 令 `W` 為任一合法胡牌型（`needed` 個面子 + 1 個眼，且每種牌 ≤ 4 張）。
> 手牌要變成 `W`，需要摸進的張數 = `|W| - Σ min(W[i], hand[i])`。
> 每一巡摸一張打一張，最後摸到的那張就是胡牌張，
> 所以 **向聽數 = (|W| - 最大重疊) - 1**，對所有 `W` 取最小。

於是問題變成「求手牌與所有合法胡牌型的最大重疊張數」，可以直接 DP。

驗算幾個例子（未副露，`|W| = 17`）：

| 手牌狀況 | 最大重疊 | 向聽數 |
| --- | --- | --- |
| 已胡（17 張剛好是胡牌型） | 17 | -1 |
| 聽牌（16 張差一張） | 16 | 0 |
| 8 組么九對子 `1199m1199p1199s1122z`（湊不出順子） | 5 組變刻子(10) + 1 組當眼(2) = 12 | 4 |

⚠️ 但「對子多」不等於離胡牌遠：`1122334455667788m` 同樣是 8 組對子，卻已經**聽牌**——
摸到 1 萬就是 `111m 234m 234m 567m 567m + 88m`，而且聽 1、2、4、5、7、8 萬六種牌。
這類反直覺的牌型正是不能用手算填測資期望值的原因。

### 3.3 DP 狀態

```
search(i, meldsLeft, pairUsed, a, b)
```

| 參數 | 意義 |
| --- | --- |
| `i` | 目前處理到的牌索引 0..33 |
| `meldsLeft` | 還需要幾個面子 |
| `pairUsed` | 眼是否已放好 |
| `a` | 由 `i-2` 起始、仍覆蓋到 `i` 的順子數 |
| `b` | 由 `i-1` 起始、仍覆蓋到 `i` 的順子數 |

在索引 `i` 決定「放幾組刻子（0/1）、由 `i` 起始幾個順子、眼放不放這裡」，
此時目標牌型在 `i` 上的張數為

```
used = 3 * 刻子 + 2 * 眼 + 由i起始的順子 + a + b        （必須 ≤ 4）
```

對重疊的貢獻是 `min(used, hand[i])`，然後轉移到 `search(i+1, …, b, 由i起始的順子)`。

掃到 `i = 34` 時，必須 `meldsLeft == 0 && pairUsed && a == 0 && b == 0` 才算合法收尾。

**花色邊界**不需要特別處理：順子只能由 1~7 起頭（`Tiles.canStartRun`），
所以 8、9 一定不會開新順子，進入下一個花色時 `a`、`b` 必為 0。

### 3.4 複雜度

狀態數 = `35 × 6 × 2 × 5 × 5 = 10,500`，每個狀態最多 20 種轉移。
用世代戳記（generation stamp）重複利用 memo 陣列，不必每次清空。

一次 `analyze()`（17 張）大約是：

```
16 種切法 × 1 次向聽計算  +  最佳切法數 × 34 次進張試探
```

實測在 JVM 上單次向聽計算是數十微秒等級，離 1 FPS 的預算（1000 ms）非常遠。

## 4. 有效進張與切牌建議

- **有效進張（16 張）**：對每一種牌 `t`，若 `shanten(hand + t) < shanten(hand)`，`t` 就是有效進張。
  剩餘張數 = `4 - 自己手上的張數 - 牌河已見張數`。
- **切牌建議（17 張）**：對每一種可打的牌，算打完之後的向聽數與進張總數，
  依「向聽數小 → 進張多 → 種類多 → 優先打字牌/么九」排序。
  打出去的那張牌本身也會進入牌河，計算剩餘張數時要再扣 1。

海底已見牌是這個 App 的核心價值：人腦記不住整個牌河，鏡頭可以。
同樣是聽兩面，「聽的牌還剩 7 張」和「只剩 1 張」是完全不同的決策。

## 5. 正確性驗證

`tools/verify_engine.py` 用三種互相獨立的方法交叉驗證（不需要 JDK，直接 `python` 執行）：

1. **最大重疊 DP** —— 與 Kotlin `ShantenCalculator` 逐行等價的移植。
2. **傳統面子/搭子分解公式** —— 結構完全不同的第二實作。
3. **暴力窮舉真值** —— 不含任何公式，只用「胡牌型定義」與「最少換幾張牌能聽牌」窮舉。

最近一次執行結果：

```
[1] DP vs 面子分解公式：1600 手，不一致 0 手
[2] 胡牌判定 (shanten==-1 vs 牌型拆解)：1600 手，不一致 0 手
[3] 暴力窮舉真值：{0: 20, 1: 20, 2: 20} 共 60 手（另含 17 張），不一致 0 手
```

Kotlin 單元測試（`ShantenCalculatorTest`）的期望值全部來自這支工具的輸出，
並在測試中額外驗證兩個不變量：摸牌後向聽數只能持平或減 1、打牌後只能持平或增加。
